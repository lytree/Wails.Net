## 测试方案设计（对标 Wails v3 / Tauri v2）

产出：`docs/development/testing-strategy.md`（战略层，与已有 `testing-guide.md` 战术层互补）。

### 上游方案要点
- **Wails v3**：纯 Go 原生 `go test` + 表驱动 + `-race` + `go cover`；手写 interface mock，无 mock 框架；有 `v3/pkg/application/internal/tests`；E2E 用 Playwright 连 dev server（:9245）。**硬伤：无 mock runtime，平台层不可测**。
- **Tauri v2**：三层清晰。① Rust 单测 + `tauri::test::MockRuntime`（`mock_builder` / `mock_context(noop_assets())` / `get_ipc_response` / `assert_ipc_response` / `INVOKE_KEY`），无真实 webview 即可建窗口跑完整 IPC；② 前端 `@tauri-apps/api/mocks`（`mockIPC` / `mockWindows` / `clearMocks` / `shouldMockEvents`）配 Vitest；③ WebDriver E2E（`@wdio/tauri-service` + embedded WebDriver server，macOS 靠内嵌 server 支持；或 `tauri-driver` 仅 Win/Linux）。**硬伤：MockRuntime 标注 unstable，且无契约保证与真实 runtime 一致**。

### 本项目现状盘点
- 已有 7 个测试工程、约 **2283 个 `[Test]`**，无框架混用（全 TUnit）。
- **GuiContract 契约测试是领先设计**：`WebviewWindowContractTests`(2237 行) + `IWebviewWindowFixture`，L1/L2/L3 分级 109 项，三平台各自实现——两个上游都没有。
- 已有 `Platform/ServerMode/`（625 行 no-op 桩）——是做 Mock 运行时的现成地基，但定位是生产降级不是测试设施。
- 关键缺口：`SourceGenerators`(1402 行) / `Runtime.Js`(1141 行) / `Events` / `Errors` 等 8 个 src 模块零测试；**无覆盖率配置**；CI 里 test-linux/android/e2e 全 `continue-on-error: true`（等于无门禁）。

### 设计决策
1. 五层金字塔 L0(编译期守卫) → L1(组件单测) → L2(MockPlatform 集成★新) → L3(GUI 契约) → L4(桌面 E2E)。
2. **`Wails.Net.Testing` 放 `src/` 作为可发布 NuGet 包**，不放 tests/——理由同 Tauri 把 `tauri::test` 放主 crate：下游用户也需要。
3. **Mock 实现必须接入 GuiContract 作为第 4 个平台**（`HasRealGuiEnvironment => true`），用 109 条契约锁住 Mock 与真实实现不漂移——这是相对 Tauri 的改进点。
4. Mock 注册走现有 `PlatformFactory.RegisterPlatformApp("mock", ...)` + `[ModuleInitializer]`，零反射，守 AGENTS.md §3.4。注意静态字典需 `ClearRegistrations()` 复原。
5. 覆盖率用 **`Microsoft.Testing.Extensions.CodeCoverage`**（项目走 MTP `dotnet run`，不是 coverlet）。
6. 源生成器测试**不能用** `Microsoft.CodeAnalysis.*.Testing` 的 Verifier 包（绑死 xUnit/NUnit/MSTest，违反 AGENTS.md）→ 手动驱动 `CSharpGeneratorDriver` + `Verify.TUnit`。
7. 建议把 AGENTS.md §3.4.6 的 `CancellationToken` 约定升级为编译期诊断（WAILS0001），§3.4.5 禁反射检查升级为自动化扫描测试。

## 前端 TS 运行时 SDK：`@wails-net/runtime`（npm 包）

产出：`packages/wails-net-runtime/`（pnpm 管理，TS 编写，自包含）。

- 目标：为 Wails.Net 前端提供自包含 IPC 传输 + 全部 46 个插件 + 全量核心命名空间的强类型封装（用户确认：自包含传输 / 包名 `@wails-net/runtime` / 全量核心+插件）。
- 关键实现：`src/internal/transport.ts` 三态通道（Server 模式 WS / 原生 postMessage / HTTP 分块≥512KB）、调用取消、双层响应解包；`fnv1a.ts` 绑定 ID 哈希（与后端 `Bindings.FNV1aHash` 一致，offsetBasis=2166136261, prime=16777619）；`core/runtime.ts` 暴露 `wails.call / bindings.call(id) / bindings.id(name) / events.* / query`。
- 协议对齐来自探索报告：所有调用走 `type:"call"` + `{name, args[]}`；`event.emit`/`drag`/`contextmenu` 无响应（fire-and-forget）；响应 `{id,type,result:{result,error}}`；`byte[]`↔Base64。
- 后端集成：仍读取 C# 注入的轻量 `window._wails` 标志（platform/isServerMode/URL）作为配置；前端改用 `import { wails } from "@wails-net/runtime"`，无需加载运行时 JS。`TypeScriptGenerator.cs` 现有 `import ... from '@wails/runtime'` 需改为 `@wails-net/runtime` 才能复用生成产物。
- 验证：本机**无网络**，pnpm 无法安装/运行（shim 损坏、corepack 缺失、npm install 也失败）→ 用仓库 examples 里的 tsc（opencode 缓存 TS 5.9.3）完成 `tsc --noEmit` 与 emit 构建，并用 node 跑通 fnv1a 向量(`a`→0xe40c292c)与响应解包/CallError 运行时校验。用户侧需 `pnpm install && pnpm build` 生成 `pnpm-lock.yaml`。
- vitest 测试 `src/internal/transport.test.ts` 已写好但本机无法跑（缺 vitest），需用户 `pnpm install` 后 `pnpm test`。

## `src/Wails.Net.Runtime.Js` 职责梳理（代码走读）

- 定位：**后端侧的「前端运行时 JS 生成器」**，纯 C# 类库（NuGet `Wails.Net.Runtime.Js`），不含 JS 构建链。唯一职责是把注入 WebView 的那段 JavaScript 拼成字符串。
- 调用链：`Win32WebviewWindow.cs:1170` / `LinuxWebviewWindow.cs:378` → `Application.GenerateRuntimeJs(isDebug)`（`Application.cs:1509`，决定 platform 与 IsServerMode，Server 模式注入 WebSocketUrl/AssetServerUrl）→ `RuntimeGenerator.Generate(options)` → ExecuteScript 注入。

## 两者重叠边界精确比对 + npm 包事件下行 P0 修复

**重叠结论（逐项比对）**：
- **重叠 22 个命名空间**（C# `GenerateApi` 全集）：call/bindings/events/window/tray/windows/screen/clipboard/dialog/menu(+MenuRole)/application/stronghold/scope/localhost/fswatch/system/power/process/fs/shell/notification/store/log。
- **npm 独有 26 个**（C# 完全没有）：http/upload/websocket/cookie/deeplink/opener/sqlite/keychain/path/fileassociation/updater/cli/globalshortcut/autostart/os/localization/app/positioner/windowstate/dpiScale + 移动端 8 插件(camera/nfc/biometric/geolocation/haptics/barcodeScanner/permissions/device)。
- **C# 独有、npm 永远无法替代的 3 项**：① `GenerateFlags` 生成 `window._wails`（npm 包 `readRuntimeFlags()` 反过来依赖它读 platform/isServerMode/URL，是**单向依赖**不是重叠）；② ContextMenu 钩子（CSS 变量驱动）；③ 无构建工具的纯 HTML 前端兜底。
- 故两者**不能互相完全替代**，C# 侧至少要保留 Flags + 钩子。

**本轮修复的 npm 包 3 个真 bug**（`packages/wails-net-runtime/src/internal/transport.ts` + `core/runtime.ts`）：
1. **[P0] 桌面模式事件全丢**：后端 `EventIPCTransport.cs:131` 走 `ExecuteScriptAsync("window._wailsEmitEvent && window._wailsEmitEvent(name,data,senderWindowId)")` 推事件，而 npm 包只监听 postMessage/WS 通道、从未挂载该全局；因后端带 `&&` 短路保护，事件被**静默丢弃且不报错**。已在 `registerDownlink()` 挂载。
2. **[P0] `on()` 未调 `ensureInit()`**：纯订阅型前端（只 `events.on`、从不主动调后端）永远不初始化传输层 → 全局不挂载、Server 模式 WS 不连接。已修。
3. **[P1] `_emitEvent` 遍历原 Set**：回调内部调 `off()`/`once()` 会改动集合导致漏派发 → 改为遍历副本 `[...set]`。
- 附带：`EventCallback` 签名扩为 `(data, senderWindowId?: number|null)`，`once` 也透传 senderWindowId（原先丢失）。
- 验证：tsc 构建通过 + node 模拟后端注入脚本跑通 7 项断言（挂载/送达/senderWindowId 透传/off/once/回调内 off 不漏派发）。注意 node 验证需先设 `globalThis.window = globalThis`，否则 `init()` 在第 84 行判非浏览器环境提前 return。

### 修复的 4 个 A2 失败（根因 → 修复）
1. **★ 根因（关键可复用）**：`WailsTestHost.InvokeAsync<T>(string, uint? windowId, params object?[] args)` 存在 C# 重载决议陷阱——首个**数值**参数会被吞成 `windowId`。`Add(2,3)` 实际成 `windowId=2, args=[3]`（得 3）；`SlowDoubleAsync(21)` 成 `windowId=21, args=[]`（得 0）。`Greet("World")` 因字符串不可转 `uint?` 才"碰巧"通过。
   - 修复：把 `windowId` 改到 `params` **之后**作可选尾参 → `(string methodName, object?[] args, uint? windowId = null)`；四个重载（`InvokeAsync<T>`/`InvokeAsync` 各含/不含 windowId）统一改为此签名。已确认无外部代码使用旧 windowId 位置重载，安全。
2. **未知绑定错误类型**：`MessageProcessor.TryDispatchCommandAsync` 在命令未找到时返回通用 `RuntimeError`，覆盖了 `BindingManager` 的 `ReferenceError`。
   - 修复：仅在 `response.Error` 含 `"Command not found"`（真正未找到）时返回 `null`，保留 `BindingManager` 的 `ReferenceError`；命令被找到但执行失败仍走 `RuntimeError`。`MethodProcessor` 调用处：`null` → 用 binding 结果；非 null → 用命令结果。（注意：此改动只影响"绑定也未命中且命令也未命中"路径，已确认无其他测试断言旧行为。）
3. **异常包装测试**：原用非泛型 `InvokeAsync(...)`（返回 `RawResult`、不抛异常）。改成泛型 `InvokeAsync<string>(...)`，其 `GetResult<T>()` 在错误时抛 `WailsInvocationException`。
4. 临时诊断文件 `DiagnosticTests.cs` 与 `EmitCompilerGeneratedFiles`、生产代码里的 trace 均已清理。
